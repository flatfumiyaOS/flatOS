# 工程表作成

現場監督・施工管理の業務で使う、案件ごとの工程表(ガントチャート)をこのプロジェクトフォルダ内で作成するスキル。過去に「大蔵様邸」の工程表を作った際の進め方とスタイルをそのまま再現する。

## 前提として毎回やること

1. **着工日とおおよその工期(何週間/何日で完工させたいか)を必ず本人にチャットで確認する。** これは案件ごとに変わり、図面からは読み取れない情報なので、絶対に自己判断で仮決めしないこと。まだ聞いていなければ、他の作業より先にこれを聞く。**工期は「実働日数」（土日・祝日を除いた実際に作業する日数）として扱う。** `build_schedule.py`が土日・祝日を自動的にスキップして日程を組むため、着工日から数えたカレンダー上の日数ではない。
2. プロジェクトフォルダ内にある該当案件の図面・改修内容(PDFや画像など)を読み込み、スコープ(どの工事が発生するか)を把握する。
3. プロジェクトフォルダ内の **「【例】工程表」** ファイルを毎回読み込み、体裁の基準にする(色・列幅・書式が変更されている可能性があるため、記憶に頼らず都度確認する)。
4. 各工事の工期(日数)や着工順の情報が図面に無い場合は、標準的なリフォーム工事の順序・工期を仮に置いて下書きを作ってよいか、本人に確認する(過去のやり取りでは「標準的な工期で仮の下書きを作成」で合意した)。ただし別の案件では別の希望があるかもしれないので、決めつけずに聞く。
5. CLAUDE.mdの方針どおり、ファイルの削除は行わない。既存の工程表を作り直す場合も、削除ではなく上書き保存か別名保存で対応する。

## 「例」から読み取るべきルール(過去の分析結果)

「【例】工程表」は以下の構成になっている。新しい案件でもこの構成を踏襲する。

- **A1**: 「〇〇様邸　改修工事」のようなタイトル。
- **B1以降(1行目)**: 月ヘッダー。工期が月をまたぐ場合は月ごとにセルを結合する(例: 7/13〜7/31は「2026年7月」、8/1〜8/2は「2026年8月」で別々に結合)。
- **2行目**: 日付(m/d形式)。B列が着工日(またはそれ以降の最初の実働日)。**土日・祝日も列として省かずに連続して並べる(歯抜けにしない)。**
- **3行目**: 曜日。2行目のセルを参照する数式(`=B2`など)を入れ、表示形式を`ddd`にする(Googleスプレッドシートの日本語ロケールでは月・火・水...と表示される)。
- **土日・祝日の列**: 作業内容は入れず、列全体(2行目〜最終行)を薄い赤(`F4CCCC`)で塗って休みだと分かるようにする。`build_schedule.py`が自動で判定・着色するため、手動で祝日を調べる必要はない(祝日判定には`jpholiday`ライブラリを使用)。
- **A列1〜3行目はテンプレート固定部分なので、絶対に文言を変更しない。**
- **4行目以降のA列**: 工種名(仮設工事、解体工事、造作工事、電気工事、給排水・ガス設備工事、空調工事、内装仕上げ工事、竣工クリーニングなど)。案件ごとに図面の内容に合わせて工種を過不足なく入れる。使わない工種は入れない。
- **各工種の行**: 該当する日の列に工事内容を短い文字列で入力。2日以上かかる工事はセルを結合する。同じ行の中で日付範囲が重ならないようにする(重ねたい場合は行を分ける)。別の行同士(=別の工種)なら同じ日程で重なってよい(並行作業)。
- **色分け**: 行ごとに異なるパステルカラーを使う。Googleスプレッドシート標準パレットの以下7色を順番に使い回す。
  `F4CCCC(赤)`, `FFF2CC(黄)`, `D9EAD3(緑)`, `D9D2E9(紫)`, `C9DAF8(青)`, `D9D9D9(グレー)`, `EAD1DC(ピンク)`
- **竣工クリーニングの行の下**: 「騒音・近隣配慮工事」のような行を追加し、近隣住民に影響が出る工事(解体の振動・騒音、断水を伴う配管切り回しなど)があれば記載する。この行だけは目立たせるために強めの赤(`E06666`)を使い、文字は白にする。該当する工事が無ければこの行は省略してよい。
- 文字は折り返し(wrap text)+中央揃えにし、印刷時に文字が隠れないようにする。フォントはArial、通常10pt、工事内容セルは8pt程度に小さくすると収まりやすい。

## 手順

1. 上記「毎回やること」で着工日・工期・図面内容を確認する。
2. 図面から工事スコープを整理し、工種(行)のリストを組み立てる。ユーザーに「この工種構成で進めます」と一度見せてから作業してもよいが、過去のやり取りでは下書きをまず作ってからフィードバックをもらう進め方だったので、迷ったら下書き優先で進めてよい。
3. `scripts/build_schedule.py` を使って xlsx を生成する。使い方はスクリプト冒頭のdocstring参照。config.jsonには title / start_date / total_days / rows(各行のlabel・タスクのstart_day/end_day/text) を入れる。**day番号(start_day/end_day)は着工日を1日目とした「実働日」の通し番号**(土日・祝日は含めない)。スクリプト側が実働日番号を実際のカレンダー日付(土日・祝日を飛ばした位置)に変換するので、タスクを組み立てる側は土日・祝日を意識せず、単純に実働日の通し番号で考えてよい。
   ```
   python3 "スキルのscripts/build_schedule.py" <config.json> "<出力先>/<案件名>_工程表.xlsx"
   ```
   出力先はプロジェクトフォルダ直下にする。
4. 生成後、openpyxlで読み戻して値・結合セル・色を検証し、意図通りか確認してから報告する(セル結合の重なりミスや色の塗り忘れがないか)。
5. Googleスプレッドシートへの反映方法は、そのセッションで使えるツールによって変わる。会話の最初に(またはこのタイミングで)Google Drive/Sheets系のツールが使えるか `ToolSearch` で確認する。
   - 使えるツールがあれば、それを使って直接Googleスプレッドシートとして作成・反映する。
   - 使えない場合は、生成したxlsxをそのままプロジェクトフォルダに保存し、「Googleドライブにアップロードして『Googleスプレッドシートとして開く』を選ぶと同じ体裁で編集できます」と案内する。新しく追加されたコネクタは同じ会話内では読み込まれず、新しいチャットで初めて使えるようになることがある点も伝える。
6. 修正依頼(工程の削除・追加、行名の変更、担当工事の移動など)が来たら、config.json相当の内容を更新して再生成し、変更点を簡潔に報告する。全部作り直すのではなく、差分だけ触るようにする。

## 過去の案件で得た教訓

- 図面に「要検討」「未定」と書かれている項目は、勝手に含めたり除いたりせず、ユーザーに確認するか、含めた上で「要確認」と一言添える。
- 新築・増築(離れ・小屋など)のように工期が読みにくい工事は、他の標準的な内装工事と同じ感覚で日数を詰めすぎないよう注意し、無理な圧縮になっていないか一声かける。
- ユーザーから「この工事は除いてください」「この工種は分けてください」のような修正依頼が来た場合、関連する行(騒音・近隣配慮工事など)に古い工事名が残っていないか合わせて確認する。
